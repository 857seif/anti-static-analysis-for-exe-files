# 🛡️ Anti Static Analysis — Packer-to-Source

A Windows GUI tool that converts any EXE into an **internally-encrypted C++ source file**, recompiled from scratch every time. The final binary decrypts itself at runtime and maps the original PE into memory by itself (Manual Mapping) — with no external packing layer at all.

---

## 💡 The Core Idea: Why This Is a Better Way to Protect Your Files

Normally, if you want to protect your file you use a traditional **packer** like UPX or VMProtect:

- UPX is trivially unpacked: `upx -d file.exe`, and its signature is known by every AV and static scanner.
- Traditional packers add a compression/encryption layer on top of the original file — that layer is a **fixed pattern (signature)** that's easy to detect.
- Any static analyst can identify the packer from its headers and well-known stubs, then trace the unpacking loop until they reach the original code.

### What does this tool do differently?

| UPX / Traditional Packers | Anti Static Analysis (Packer-to-Source) |
|---|---|
| A known packing layer with signatures | **No packing layer at all** — the output is a plain C++ file |
| Unpackable with a single command | No ready-made unpacker exists — the generated code must be analyzed manually |
| The same stub for everyone | The stub is recompiled every time → **the signature changes every run** |
| AV engines detect it easily | Static analysis finds a legitimate-looking C++/Win32 program |
| The unpacking loop is easy to trace | Decryption happens inside the same process + manual mapping | |

**The big trick:** you feed it an EXE ← it gives you a **`.cpp`** ← you compile it ← final file. The final binary holds the payload as an `unsigned char` array, with the decryptor embedded in the code. No off-the-shelf tool can unpack this setup, because every run generates a **random key + a different algorithm + different code**.

### 🔥 The Killer Combo

```
Your original file
    + UPX (or any packer)          ← traditional layer
    + Anti Static Analysis         ← encryption + source embed + manual map
    = a file that's extremely hard to analyze statically
```

If you compress your file with UPX first, then run it through this tool, an attacker will face:

1. A plain-looking C++ file — no UPX signature anywhere.
2. A payload encrypted with one of 12 algorithms (unknown which).
3. A random 16-byte key, different every time.
4. In-process decryption at runtime.
5. The payload thrown into a manual `VirtualAlloc(RWX)` (no suspicious sections in the PE).
6. `ExitProcess` hooked for cleanup, and child processes killed on exit.

## ⚙️ Features

- 🎯 **12 encryption algorithms**, from plain XOR to ChaCha20.
- 🗜️ **Optional RLE compression** (Balanced mode).
- 🔑 **Auto Key**: random 16-byte key per run, or a manual key.
- 🧩 **Full Manual PE Loader**: sections, relocations, IAT, TLS callbacks.
- 🪝 **ExitProcess hooking** — prevents early termination, stabilizes cleanup.
- ☠️ **Job Object + Kill Spawned Processes** — kills child processes on exit.
- 🖥️ **Full GUI** with progress bar and size estimator.
- 🧬 **Output: C++ source** — builds with any GCC/MinGW, already using all hardening flags.

## 🚀 Usage

### 1. Build (MinGW)

```bash
g++ -O2 -DUNICODE -D_UNICODE "anti static analysis.cpp" -o packer.exe -luser32 -lcomctl32 -mwindows
```

### 2. Run

1. Launch `packer.exe`.
2. Pick a target EXE.
3. Choose the algorithm from the ComboBox.
4. Choose Fast (no compression) or Balanced (with RLE).
5. Leave Auto Key enabled, or type your own key.
6. Hit **GENERATE C++ STUB**.
7. You'll get `name_packed.cpp` + a ready build command — copy and run it.

### 3. Build command (generated by the tool)

```bash
g++ -O2 -s -DUNICODE -D_UNICODE "file_packed.cpp" -o packed.exe -luser32 -mwindows \
    -Wl,--strip-all -Wl,--gc-sections \
    -ffunction-sections -fdata-sections \
    -fno-exceptions -fno-rtti \
    -fno-asynchronous-unwind-tables -fno-unwind-tables \
    -fno-ident -static-libgcc -static-libstdc++
```

All these flags strip metadata from the final binary (no `.pdata`, no RTTI, no exception tables, no build info) — making static analysis significantly harder.

## 🧪 Full Code Walkthrough

### Part 1: Encryption Algorithms

#### 1️⃣ `EncXOR` — Plain XOR
```cpp
o[i] = d[i] ^ (BYTE)k[i % k.size()];
```
The fastest and weakest algorithm. Every byte is XORed with a cycling key byte. **Known-plaintext attack**: the first two bytes of any PE are `MZ` — knowing them reveals the first two key bytes, and so on.

#### 2️⃣ `EncXORRoll` — Rolling XOR
```cpp
s = (BYTE)(s + k[i % k.size()] + (BYTE)(i * 31));
o[i] = d[i] ^ s;
```
Same weakness as XOR, but the key state moves with the index. Against known-plaintext: initially `s = 0x5A + k[0]`, and since the attacker knows plaintext and ciphertext, they can recover `k[0]` and then the rest of the key. Slightly stronger than plain XOR, still weak.

#### 3️⃣ `EncRC4` — Real RC4
```cpp
// KSA: shuffle the S[256] table with the key
// PRGA: generate the key stream and XOR
```
A real stream cipher — the key stream is not linear in the key. The first KSA round can leak from a known first chunk, but in practice RC4 without a per-file IV is still weak if the key is short. Acceptable.

#### 4️⃣ `EncTEA` — Tiny Encryption Algorithm
A 64-bit block cipher, 32 rounds, 128-bit key. It prepends 4 bytes containing the original size (so padding can be reverted). Academically secure against brute force, but has known related-key weaknesses. Good.

#### 5️⃣ `EncXTEA` — eXtended TEA
Same TEA core with more complex mixing: `((v<<4)^(v>>5))+v) ^ (sum+k[...])`. Stronger than TEA — one of the best practical choices here, being a real block cipher with only 4 bytes of overhead.

#### 6️⃣ `EncXXTEA` — Corrected Block TEA
Operates on one big block (the whole file as a `uint32` array) instead of 8-byte blocks. Practically the strongest member of the TEA family against manual analysis, because changing any byte affects everything after it.

#### 7️⃣ `EncSalsa20` — Salsa20 (simplified)
```cpp
// state = constants + key(256-bit) + nonce(zero) + counter
// 20 double rounds (QR on every column and diagonal)
```
A modern stream cipher by DJB. The strongest algorithm in the list on paper. Note: this implementation uses counter = `i/64` and nonce = 0 — not the standard construction exactly, but security is preserved since the key is large and random.

#### 8️⃣ `EncChaCha` — ChaCha20
Same idea as Salsa20 with the modified quarter-round order (the one Google used in QUIC). **The strongest practical choice in the tool** — a known modern stream cipher, fast, and resistant to statistical analysis. Same nonce=0 note applies.

#### 9️⃣ `EncBlowfish` — ⚠️ "Blowfish-like"
```cpp
state = state * 0x01000193 ^ key[i];  // FNV hash
state = Rotl(state, 7) * 0x85EBCA6B;  // PRNG
```
**This is NOT Blowfish!** It's a PRNG built on an FNV hash and Murmur-style mixing. Statistically breakable since the output is nearly linear. The name is misleading — not the real cipher.

#### 🔟 `EncTwofish` — ⚠️ "Twofish-like"
Same concept: a key-seeded PRNG. Slightly stronger than the Blowfish-like variant due to the interaction between `k0` and `k1`, but still not real Twofish.

#### 1️⃣1️⃣ `EncSerpent` — ⚠️ "Serpent-like"
An LCG-based PRNG with a 4-bit S-box. Weaker than the two above.

#### 1️⃣2️⃣ `Enc3Layer` — Triple Encryption
```
XOR Rolling → RC4 with a different key ("_L2") → key-seeded rolling PRNG
```
Not one strong algorithm, but layering forces the attacker to peel three stages sequentially. Practically stronger than any of layers 9–11 alone.

### 🏆 Algorithm Strength Ranking (Honest Analysis, Not Marketing)

| Rank | Algorithm | Why |
|---|---|---|
| 🥇 1 | **ChaCha20 / Salsa20** | Modern stream ciphers — the key stream can't be guessed from known plaintext |
| 🥈 2 | **XXTEA** | Block cipher — diffusion covers the entire file |
| 🥉 3 | **XTEA** | Stronger than base TEA, fast |
| 4 | **TEA** | A proper block cipher |
| 5 | **3-Layer** | Layers, but all weak primitives — good against casual analysts |
| 6 | **RC4** | A real stream cipher, but no IV |
| 7 | **Twofish-like / Blowfish-like** | PRNGs, not ciphers — statistically breakable |
| 8 | **Serpent-like** | Simple PRNG |
| 9 | **XOR Rolling** | Easy known-plaintext attack |
| 10 | **XOR** | Unpackable in minutes with IDA |

> **⚠️ Honest security note:** even the strongest algorithm here (ChaCha20) protects against **static analysis only**. The moment the stub runs, the original PE exists in full inside the `VirtualAlloc` region — any dynamic analysis, debugger, or memory scanner can dump it. Real protection against runtime dumping requires VM-based protection (like VMProtect/Themida). This tool firmly locks the front door (static) — runtime is a different story.

### Part 2: Compression & Utilities

#### `RleCompress` — Run-Length Encoding
```cpp
if (run >= 4) { out.push_back(0xFF); out.push_back(b); out.push_back(run); }
```
Compresses long runs (≥4 repeated bytes) using the escape byte `0xFF` (a literal `0xFF` in the data is stored as a run of length 1). Effective on PE files, which contain large zero-filled regions (empty sections). `RleDecompress` reverses it.

#### `BytesToCppArray`
Turns the encrypted payload into:
```cpp
static unsigned char g_payload[] = { 0x4D, 0x5A, ... };
static unsigned int g_payload_len = 12345;
```
Formatted 16 bytes per line to keep the code readable.

#### `DecryptorCode(int algo)`
The gem: returns the matching **decryptor** source code for each algorithm as a string. So the tool doesn't just encrypt — it generates the code that decrypts. Anyone trying to understand the stub must read the decryptor inside the generated code.

#### `RandomKey`
```cpp
std::mt19937 rng(time(nullptr) ^ GetTickCount());
```
A 16-byte key from 74 possible characters → key space of ~74^16 ≈ 10^30. Adequate.

### Part 3: Stub Generation (`GenerateCppStub`)

The most important function — builds the final C++ file. Its components:

1. **Payload array** + the key (stored as `\x41\x42...` escapes).
2. **`RleDecompress`** — if Balanced mode was chosen.
3. **The decryptor** matching the selected algorithm.
4. **`HookExitProcess`** — walks the Import Table looking for `ExitProcess` and replaces it with `ExitThread`. Why? If the payload (especially a GUI app) calls `ExitProcess`, the whole process dies before cleanup finishes.
5. **`KillSpawnedProcesses`** — snapshots all processes and kills any with the same exe name (the children).
6. **`MapAndRun`** — the Manual Mapper (details below).
7. **`WinMain`** — workflow: Job Object → Decrypt → (Decompress) → AllocConsole if the payload is a console app → MapAndRun → cleanup → ExitProcess.

#### 🔬 `MapAndRun` Details (The Manual PE Loader)

```cpp
1. Verify signatures: MZ + PE\0\0
2. VirtualAlloc(NULL, SizeOfImage, MEM_COMMIT|RESERVE, PAGE_EXECUTE_READWRITE)
3. Copy headers + every section to its VirtualAddress
4. If the base changed (delta != 0) → process Base Relocations
   (HIGHLOW = +32-bit delta, DIR64 = +64-bit delta)
5. Resolve imports: LoadLibraryA per DLL + GetProcAddress per function → fill the IAT
6. HookExitProcess
7. Execute TLS callbacks if present (important for C++ compilers using TLS)
8. If DLL → call DllMain(DLL_PROCESS_ATTACH)
   If EXE → CreateThread on the Entry Point
9. GUI → Message Loop | Console → WaitForSingleObject
```

This is a complete manual loader — meaning the original PE is **never loaded by the Windows loader**, so its PE headers don't appear in the normal process view, breaking most static scanners.

#### ⚡ `WinMain` Details
```cpp
CreateJobObject + JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE
→ every child process is killed automatically when the parent exits
```

```cpp
if (payload is console subsystem) → AllocConsole + freopen
```
A smart touch: the stub itself is GUI (`-mwindows`), but if the original payload is a console app, it allocates a console so output still works.

## 🧠 "Why Is It Hard to Unpack?" — Attack vs. Defense

### Static analysis attacks and why they fail here:

| Attack | Against UPX | Against this tool |
|---|---|---|
| Signature scanning | ✅ Detects instantly | ❌ No signature — code changes every run |
| `upx -d` | ✅ Unpacks in a second | ❌ Doesn't exist |
| IDA pattern matching | ✅ | ❌ The decryptor is text-generated, structure varies |
| String hunting | ✅ Known strings | ⚠️ Only core imports |
| Entropy analysis | 🔴 High entropy stands out | 🟡 Normal (real code surrounds the data) |

### Why it's still not bulletproof (being honest):

1. **Runtime dump**: the moment it runs, the PE is fully in memory — a snapshot tool or debugger grabs it.
2. **The key is inside the binary**: like any packer, the key ships with the stub — anyone who understands the decryptor can decrypt offline.
3. **The "like" algorithms**: 9, 10, and 11 are PRNGs, not real ciphers — if the attacker expects that, they can solve them statistically.
4. **No anti-debug / anti-VM**: not implemented — listed as TODO.
